## 1. 从固定两次请求到 Agent Loop

昨天的程序固定最多请求模型两次，只处理第一个工具调用。今天完成了：

| 功能 | 当前行为 |
| --- | --- |
| 请求循环 | 最多执行 5 轮，正常完成时提前结束 |
| 多工具调用 | 遍历本轮回复中的所有调用，按顺序执行 |
| 消息历史 | 累积模型调用消息和工具结果 |
| 停止条件 | 区分正常回答、次数耗尽和错误退出 |
| 日志 | 显示轮数、消息数量、调用详情和停止原因 |

已经通过真实运行验证普通回答、一轮多个调用、连续多轮调用和两种上限边界。当前工具有 `add` 和 `read_note`，模型请求与消息管理遵循同一套循环。

## 2. 模型、控制程序、工具分别负责什么

| 角色 | 当前项目中的对应内容 | 职责 |
| --- | --- | --- |
| 模型 | API 返回回复的 DeepSeek | 根据问题和历史，提出工具调用或生成回答 |
| 控制程序 | `main.py` 中的请求、判断与循环逻辑 | 请求模型、校验参数、执行工具、保存消息、决定停止 |
| 工具 | `add`、`read_note` | 执行具体的本地操作并返回数据 |

模型返回“请调用 `add`”时，本地函数不会自动执行。控制程序必须读取工具名和参数，再调用对应函数。

`read_note` 返回的是实际笔记正文；模型收到正文后负责理解和总结。只发送文件名，不等于模型已经获得文件内容。

在工具调用协议中，工具的实际执行由客户端程序完成，结果随后作为工具消息回传。参考：[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)。

## 3. Agent Loop 的整体流程

```text
初始化一次
  定义函数与工具列表 → 获取密钥 → 创建客户端 → 初始化 messages
    ↓
开始外层循环，最多请求 5 轮
    ↓
发送 messages 和 tools → 收到模型回复
    ↓
是否有工具调用？
    ├─ 没有 → 打印最终回答 → break → 正常结束
    └─ 有
        ↓
      保存一次完整的 assistant 调用消息
        ↓
      遍历本轮所有工具调用
        解析参数 → 校验 → 执行 → 记录日志 → 追加对应 tool 消息
        ↓
      本轮调用全部处理完，进入下一轮模型请求

若外层循环自然耗尽 → 显示“达到最大轮数，尚未获得最终答案”
若参数或工具执行出错并抛出 SystemExit → 直接退出程序
```

### 3.1 什么是一轮

本文约定：外层循环中调用一次模型 SDK 请求方法，算一轮。工具执行次数另算。

“先算 137＋289，再把结果加 100”的真实实验使用了：

| 轮次 | 模型返回 | 本地执行 |
| --- | --- | --- |
| 1 | 请求 `add(137, 289)` | 得到 426 |
| 2 | 请求 `add(426, 100)` | 得到 526 |
| 3 | 最终回答 526 | 无工具执行，结束 |

所以是 **3 轮模型请求、2 次工具执行**。最后生成普通回答也占一轮。

日志中的轮数统计的是程序发起的 SDK 调用次数，不是严格的底层 HTTP 尝试次数；若 SDK 内部重试，请求尝试数可能不同。

### 3.2 哪些放在循环外，哪些放在循环内

| 循环外：准备一次 | 循环内：每轮重复 |
| --- | --- |
| 函数定义、工具说明 | 请求模型、获取回复 |
| 密钥检查、客户端创建 | 判断是否有工具调用 |
| 初始 `system`、`user` 消息 | 解析、校验、执行工具 |
|  | 追加调用与结果、决定是否停止 |

`messages` 不能每轮重置。重置后，模型看不到先前的工具结果，可能反复请求第一步计算。

## 4. Python 循环与 `for … else`（今天的新语法）

### 4.1 `for`、`while`、`break`、`continue`

`for` 按可迭代对象提供的元素依次执行；`while` 在条件为真时继续。今天使用 `for i in range(5)`：`i` 依次为 0、1、2、3、4，所以日志打印 `i + 1`。

`break` 退出所在的最内层循环；`continue` 跳过本轮剩余部分，进入下一次迭代。执行到循环体末尾也会自然进入下一轮，不一定需要 `continue`。

模型给出普通回答后应当 `break`。误用 `continue` 会继续发送当时的 `messages`，造成多余请求；是否包含刚生成的回答，取决于有没有追加它。当前代码不会把最终普通回答追加到历史。

### 4.2 `else` 为什么能跟在 `for` 后面

`for` 自然耗尽时执行它的 `else`；通过 `break` 退出时跳过它。`return` 或向外传播的异常提前终止执行，也不会执行这个 `else`。空迭代对象同样属于自然耗尽。

参考：[Python 循环控制与 else](https://docs.python.org/3/tutorial/controlflow.html#else-clauses-on-loops)。

下面是只展示结构的复盘示意，不是替代项目实现：

```python
for item in [1, 2, 3]:
    if item == 2:
        break
else:
    print("自然耗尽")
```

这个例子遇到 2 就退出，不会打印“自然耗尽”。删除其中的 `if` 与 `break`、改为打印每个元素后，循环会完整遍历，随后进入 `else`。

### 4.3 对应到今天的停止逻辑

| 实际情况 | 是否执行外层 `else` | 项目中的意义 |
| --- | --- | --- |
| 某轮没有工具调用，执行 `break` | 否 | 正常回答并结束 |
| 最后一轮仍有工具调用，处理后自然耗尽 | 是 | 尚未获得最终回答 |
| 最后一轮直接回答，并执行 `break` | 否 | 恰好在上限内正常完成 |
| 抛出 `SystemExit` | 否 | 因错误退出 |

最大轮数是“最多允许多少轮”，不是“必须执行多少轮”。

最后一轮工具执行成功后，仍能把结果追加到本地 `messages`；只是没有下一轮请求将它发送出去。因此，“工具执行成功”不能直接等同于“整个任务已完成”。

### 4.4 缩进决定 `else` 属于谁

当前代码有两层循环和多层条件：

- 外层 `for`：控制模型请求轮次。
- 内层 `for`：遍历本轮工具调用。
- 工具分发的 `if / elif / else`：选择 `add`、`read_note`，或拒绝未知工具。
- 判断 `tool_calls` 的 `else`：处理最终普通回答。
- 与最外层 `for` 对齐的 `else`：处理次数耗尽。

普通回答分支中的 `break` 位于内层工具遍历之外，所以它退出的是外层请求循环。未知工具使用 `SystemExit`，会结束整个程序，而不只是退出内层遍历。

轮数上限与请求超时不同：轮数限制请求多少次，超时限制一次请求等待多久。今天的 5 轮上限也不是精确的费用或总耗时上限。

## 5. `messages`：下一轮为什么知道前面发生了什么

### 5.1 两种消息各记录什么

| 消息 | 内容 | 用途 |
| --- | --- | --- |
| `assistant` 工具调用消息 | 模型本轮提出的所有调用，包含名称、参数、ID | 记录模型要求执行什么 |
| `tool` 结果消息 | 某一次调用的执行结果和对应 ID | 记录该调用实际得到了什么 |

当前代码使用 `messages.append(response_message)` 保存 SDK 返回的消息对象。初始消息和工具结果则由 Python 字典构造；当前代码里的列表并不是所有元素都为字典。

`tool_call_id` 是调用请求与结果之间的关联编号。同一个工具可以调用多次，只靠工具名无法区分每一次调用。

工具结果采用以下字段（来自现有代码）：

```python
messages.append(
    {
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": str(result),
    }
)
```

求和结果先转成字符串；`read_note` 已经返回字符串，因此这里再次调用 `str` 是多余但无害的。

### 5.2 一轮多个调用与连续多轮调用

“分别算两道独立加法”可能由模型在一轮中提出两个调用；“先拿到一个结果，再继续下一步”可以分成连续两轮调用。具体路径需要观察日志，不能仅凭提示词假定。

每轮有 N 个调用时，在全部执行成功的情况下：

**新增消息数 = 1 条完整 assistant 消息 + N 条 tool 结果消息。**

| 场景 | 下一轮发送消息数的变化 |
| --- | --- |
| 初始 2 条，一轮提出 2 个调用 | 2 → 5 |
| 初始 2 条，连续两轮各提出 1 个调用 | 2 → 4 → 6 |

完整 `assistant` 消息放在工具遍历前，只追加一次；每个 `tool` 结果放在遍历内分别追加。全部调用处理完，才进入下一轮请求。

一轮提出多个调用，不等于本地并行执行。当前内层 `for` 是按顺序执行的。

### 5.3 今天实际遇到的字段错误

曾把工具消息中的 `content` 写成 `message`。

构造这个字典本身符合 Python 语法，所以本地不会立即报语法错误。但下一轮发送给 API 时，工具结果缺少正确字段，导致请求出错。修正为 `content` 后，用户确认运行恢复正常。

记忆方式：`response_message` 可以是自己起的变量名；协议中的 `role`、`tool_call_id`、`content` 则必须按规定填写。

## 6. 工具分发与参数校验

工具说明告诉模型有哪些动作，控制程序根据 `tool_call.function.name` 选择本地函数。当前通过 `if / elif / else` 分别处理 `add`、`read_note` 和未知工具。

`function.arguments` 是 JSON 文本。执行前先用 `json.loads` 解析，再检查解析结果是否为字典、必填参数是否齐全、参数类型是否正确。JSON 解析成功并不保证结果是对象，也不保证符合工具要求。

`add` 检查 `a`、`b` 为数字，`read_note` 检查 `note_name` 为字符串。当前 `add` 使用精确的 `int`、`float` 类型判断，因此会拒绝布尔值。

工具声明、参数校验、实际函数执行是不同步骤。Schema 和 Python 类型注解都不能替代这里实际执行的本地检查。

详细 JSON 入门见 [Tool Calling 笔记](tool-calling.md)；读取工具的参数与异常见 [read_note 笔记](read-note.md)。

## 7. 日志：验证过程，而不只看答案

| 日志内容 | 能判断什么 |
| --- | --- |
| 第几轮调用 SDK | 循环是否继续、是否遵守上限 |
| 待发送消息数量 | 历史是否正确累积 |
| 本轮工具调用数 | 普通回答还是工具调用，有几个调用 |
| 工具名、调用 ID、参数 | 实际请求执行什么 |
| 执行结果或错误 | 工具是否成功 |
| 结束提示 | 正常完成、达到上限，还是错误退出 |

正确答案不能单独证明调用流程正确。例如输出 526，不等于发生了两轮工具调用；必须查看日志中实际发生的请求、参数和结果。

## 9. 当前边界

- 输入仍写在代码中，没有终端多轮聊天交互。
- `messages` 只保存在本次运行的内存中，没有跨运行保存历史。
- 工具逐个执行，没有并行调度。
- 工具失败采用退出程序的策略，没有把失败回传给模型并自动恢复。
- 模型请求失败尚无专门捕获，应用层没有显式设计请求超时和重试策略。
- 5 轮限制不等于精确限制底层 HTTP 尝试次数、总时间或费用。
- 消息历史没有长度控制；长工具结果可能占用较多上下文。
- 两个工具分支保留部分重复逻辑，后续可按实际需要整理。

当前默认演示是读取 `basics.md`，最大轮数已恢复为 5。模型名称和请求配置对应当天版本，不保证未来 API 配置不变。
