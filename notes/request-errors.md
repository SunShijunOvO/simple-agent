## 2. 请求失败时，赋值到底发生了什么

```python
response = client.chat.completions.create(...)
```

这是一段结构示意。执行赋值时，先计算等号右侧，成功返回后才把结果绑定给左侧变量。

今天最初的理解是“请求失败后，`response` 的内容不可预期”。更准确的解释是：**右侧抛出异常，赋值没有完成，正常执行流程被打断。**

| 情况 | `response` 的状态 | 程序流程 |
| --- | --- | --- |
| 第一次请求成功 | 绑定本次响应 | 继续处理回复 |
| 第一次请求抛出异常 | 此前未定义，因此仍未定义 | 转入匹配的异常处理；没有处理则向外传播 |
| 前面成功，后面某轮请求抛出异常 | 保留上一次成功赋的值 | 不会自动变成 `None`，也不会自动更新 |

当前请求语句处于脚本顶层。如果首次失败后仅打印错误却继续读取未定义的 `response`，就可能出现 `NameError`；后续轮次失败后继续读取，则可能误用上一轮响应。这两种后果是代码推演，今天没有额外运行这类错误示例。

因此，捕获异常之后做什么同样重要。当前选择退出程序，让成功路径只在请求成功后执行。

## 3. 今天增加的异常处理

以下为当前实现的相关片段；客户端和消息初始化省略：

```python
from openai import OpenAI, APIError

# 位于模型请求循环中
try:
    response = client.chat.completions.create(
        model="deepseek-flash",
        tools=tools,
        messages=messages,
        stream=False,
        extra_body={"thinking": {"type": "disabled"}},
    )
except APIError as exc:
    raise SystemExit(f"模型请求失败：{exc}")

response_message = response.choices[0].message
```

`try` 只包住请求操作。请求抛出匹配的异常时，`except` 将异常对象绑定给 `exc`，f-string 用它生成具体的错误说明，`SystemExit` 随后结束程序。此时既不会读取 `response.choices`，也不会执行循环末尾的次数耗尽提示。

`APIError` 是该 SDK 的 API 异常基类。捕获父类也能捕获子类，和昨天使用 `OSError` 捕获 `FileNotFoundError` 的思路相同。本次在已安装 SDK 中检查到的继承关系包括：

```text
APIError
├── APIStatusError
│   └── AuthenticationError
└── APIConnectionError
    └── APITimeoutError
```

这是相关类型的节选，不是完整异常列表。因此无效密钥产生的认证异常能进入当前分支。连接及超时异常的继承关系也已检查，但今天没有制造相应故障进行真实运行验证。

`APIError` 并不代表所有 Python 异常。例如代码自身的 `TypeError`、`IndexError` 不会因此被统一捕获；请求成功后提取回复的语句也在这个 `try` 之外。

参考：[OpenAI SDK 官方错误处理示例](https://developers.openai.com/api/docs/guides/error-codes#handling-errors)。项目仍通过该 SDK 请求 DeepSeek，捕获的是 SDK 抛出的异常。

今天没有新增应用层重试。已安装 SDK 的客户端构造参数中，`max_retries` 默认值为 `2`，所以“程序没有自己编写重试循环”不等于“SDK 对任何失败都不会重试”；也不能把一次 SDK 调用直接当成恰好一次底层 HTTP 尝试。这里没有验证各类错误实际重试了几次。

## 4. 退出状态码与 HTTP 状态码

### 4.1 程序交给终端的结果标记

退出状态码用来让操作系统、Shell 或其他程序判断命令的执行结果。通常 `0` 表示成功，非 `0` 表示失败或其他需要区分的结果，具体非零值的含义由程序约定。

```python
raise SystemExit(0)              # 退出状态码为 0
raise SystemExit(2)              # 退出状态码为 2
raise SystemExit("模型请求失败")  # 向标准错误输出文字，退出状态码为 1
```

当前程序采用第三种写法：文字给人解释原因，状态码给其他程序判断结果。

在 Bash 中，`$?` 保存上一条命令的退出状态。检查时紧接目标命令执行：

```bash
python main.py
echo $?
```

中间运行其他命令会改变 `$?`；第二次再执行 `echo $?` 时，检查到的已经是前一次 `echo` 的状态。

### 4.2 两个不同层面的数字

| 数字 | 来自哪里 | 今天表示什么 |
| --- | --- | --- |
| HTTP `401` | API 服务返回的响应 | 无效密钥导致认证失败 |
| 退出状态码 `1` | Python 程序退出时交给 Shell | `SystemExit` 携带错误字符串退出 |
| 退出状态码 `0` | Python 程序退出时交给 Shell | 正常运行到结束 |

认证失败时，返回错误的是 API 服务，没有得到模型生成的正常回答。程序退出状态也不会自动等于 HTTP 状态码。

### 4.3 打印失败提示不等于返回失败状态

当前轮数耗尽分支只有 `print(...)`，随后程序运行到末尾。根据现有代码，这条路径会正常退出，状态码为 `0`，尽管任务尚未得到最终答案。

这是本次阅读代码得出的结论；今天没有新增轮数耗尽的退出码实测，也没有修改这个行为。后续若需要让其他脚本区分“任务完成”和“次数耗尽”，可以再设计对应的退出状态。

## 6. 今天复习中纠正的理解

### 6.1 工具成功与整个任务完成

本地工具成功后，结果先追加到内存中的 `messages`，到下一轮请求时模型才会收到它。模型收到结果后仍可能继续申请工具，直到给出最终回答。

当前正常读取案例的第二轮消息数为 `4`：初始 `system`、`user` 两条，加上一条模型的 `assistant` 调用消息和一条本地 `tool` 结果消息。

### 6.2 工具名与调用 ID

工具名说明执行哪个工具，调用 ID 用于关联一次具体调用与它的结果。同一轮两次 `add` 不能只靠名称区分；每条结果都要使用对应请求给出的 ID。程序应原样使用该 ID，不自己编造，也不假定它在所有会话中全局唯一。

如果删掉 `messages.append(response_message)`，历史就缺少此前的调用请求。此时 `tool` 结果的 ID 找不到对应请求。工具的使用说明仍由 `tools` 提供，缺少的是这一次调用的名称、参数和 ID 记录，而不是工具定义。

### 6.3 `for ... else`：自然耗尽与 `break`

临时使用 `range(1)` 且第一轮请求工具时，本地执行后即使追加了结果，也没有第二轮请求发送它。循环自然耗尽，执行 `for` 对应的 `else`。

“自然耗尽”与 `break` 不同：`break` 会跳过循环的 `else`。向外传播的 `SystemExit` 也不会执行这个 `else`。最后生成普通回答同样占一次模型请求，所以 README 写的是“最多请求模型 5 轮”。

### 6.4 路径拼接不保证目标在笔记目录内

| `note_name` | 拼接与解析结果 |
| --- | --- |
| `basics.md` | 项目 `notes/basics.md` |
| `../main.py` | 项目根目录的 `main.py` |
| `/tmp/example.md` | 绝对路径覆盖前面的目录，目标为 `/tmp/example.md` |

代码不会自动补 `.md`。`.resolve()` 还会解析符号链接，因此先解析目标路径，再通过 `.is_relative_to(notes_dir)` 检查范围。详细校验顺序见 [read_note 笔记](read-note.md)。

### 6.5 `.resolve()` 报错是优先级问题

今天讲解时曾说“点号连接是从右至左的”，这不是正确原因。**属性访问和方法调用的优先级高于这里的 `/` 运算。**

```python
# 错误：会尝试对字符串 "notes" 调用 resolve()
Path(__file__).resolve().parent / "notes".resolve()

# 正确：先拼接成 Path 对象，再解析拼接后的路径
(Path(__file__).resolve().parent / "notes").resolve()
```

连续方法调用中，后一步操作前一步的结果。不能用“点号从右往左执行”来解释。括号明确指定先完成整个路径拼接。

### 6.6 `with` 关闭文件，不等于销毁对象

```python
with open(note_path, "r", encoding="utf-8") as note:
    return note.read()
```

实际顺序：读取正文字符串 → 准备返回值 → 离开 `with` 并关闭文件 → 调用者收到字符串。

Python 的 `with` 使用上下文管理器协议：进入时调用 `__enter__()`，正常离开或由 `return`、异常离开时调用 `__exit__()`。对于这里的文件对象，退出处理负责关闭文件。这是在正常 Python 控制流程中的保证，不是进程被强制终止时的保证。

可以把自动清理资源的思想与 C++ RAII 类比，但机制不同：这里不依赖析构或垃圾回收。`with` 也不创建独立的变量作用域；文件关闭后，对象仍可能被变量引用。

以下为讲解示例，今天没有另行运行它：

```python
with open("notes/basics.md", encoding="utf-8") as note:
    text = note.read()

print(note.closed)  # 预期为 True：文件已关闭
print(text)         # 读出的正文仍然可用
```

## 7. 项目讲解参考稿

> 这个项目用 Python 和 DeepSeek API 实现了一个最小 Agent。它可以根据用户问题请求本地工具，目前支持计算两个数字的和，以及读取项目笔记目录中的 Markdown 正文并交给模型总结。
>
> 程序先把用户问题、消息历史和工具说明发送给模型。模型提出工具调用后，由 Python 解析、校验参数并执行工具，再把模型的调用请求和本地执行结果一起保存到消息历史，进入下一轮请求。工具结果携带对应的调用 ID，因此同一个工具被调用多次时也能逐次对应。
>
> 模型不再请求工具时，程序输出最终回答并结束；最多允许请求模型五轮，如果次数耗尽还没得到回答，就提示任务尚未完成。遇到已处理的工具错误或模型请求异常时，会显示原因并退出。
>
> 我在文件路径处理中遇到过方法调用对象错误：把 `.resolve()` 直接写在字符串后面，程序就尝试调用字符串不存在的方法。后来用括号让程序先完成路径拼接，再对 Path 对象解析路径，解决了问题。此外还要检查解析后的路径范围，因为 `../`、绝对路径和符号链接都可能让目标落到笔记目录之外。
>
> 今天新增了模型请求异常处理，并验证了无效密钥时返回认证错误、程序以状态码 1 退出，以及正常读取笔记后以状态码 0 结束。目前工具错误仍会导致退出，没有回传给模型尝试修正；输入写在代码中，历史也没有跨运行保存，长笔记还没有大小限制。
